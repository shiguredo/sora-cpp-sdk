# BaseRenderer テストが描画前の初期状態を成功と判定する問題を修正する

- Created: 2026-10-02
- Completed: {YYYY-MM-DD}
- Branch: feature/fix-base-renderer-test-render-wait
- Polished: {YYYY-MM-DD}

## 目的

`BaseRenderer` テストの待機条件に実際の描画完了を含め、描画スレッドの実行タイミングによる CI の間欠失敗を防ぐ。
極小ウィンドウのテストが、フレーム注入と描画の継続を実際に確認できるようにする。

## 現状

### 発生事象

2026-10-02 の [ci run 36951671967 の Windows ジョブ](https://github.com/shiguredo/sora-cpp-sdk/actions/runs/36951671967/job/110665753245) で、ビルド後の `base_renderer.exe` が失敗した。
失敗したケースは「BaseRenderer が極小ウィンドウで 0 寸法の枠になっても abort しない」である。

```text
REQUIRE( renderer.CanvasWidth() == 1 )
with expansion:
  0 == 1
with message:
  RectToActualString(actual) := "[]"

test cases: 10 | 9 passed | 1 failed
assertions: 26 | 25 passed | 1 failed
```

`base_renderer.exe` が終了コード 42 を返し、`run.py` の `_build()` が `CalledProcessError` で停止した。
前日の [Windows ジョブ](https://github.com/shiguredo/sora-cpp-sdk/actions/runs/36802470776/job/110179635937) は全 10 ケースが成功している。
両ジョブのコミットは `cb8f1e3c92e1d70aecfbb0148211f5a80feb1862`、runner image は `windows-2022` の `20260927.320.1` で一致する。

### 原因

`test/base_renderer.cpp` の `TestRenderer` は、`canvas_width_` / `canvas_height_` を `0`、`sink_infos_` を空で初期化する。
キャンバス寸法と描画結果は、描画スレッドから `TestRenderer::Render()` が呼ばれたときに初めて更新される。

極小ウィンドウのケースは `TestRenderer::WaitUntil()` に `actual.empty()` を渡している。
`WaitUntil()` の `cv_.wait_for()` は待機開始時にも述語を評価するため、初回描画前の空の `sink_infos_` だけで成功を返せる。
テストスレッドが先に進むと、`CanvasWidth()` は初期値の `0` を返す。
共有データは mutex で保護されているが、待機条件が描画済みであることを要求していない。

また、`TrackFixture::StartInjection()` は注入スレッドを起動してすぐに戻る。
空の描画結果だけでは、各ソースの `InjectFrame()` が完了したことも確認できない。
別の極小枠のケース「BaseRenderer が極小の枠でフィット寸法が 0 になっても abort しない」も、処理完了の確認に固定の 200 ms 待機を使っている。

## 設計方針

### 描画済み状態を待機条件に含める

- `TestRenderer` に描画回数を追加する。`Render()` 内で、キャンバス寸法と描画結果の更新が完了した後、同じ `mutex_` の保護下で増加させて `cv_` へ通知する。
- `WaitUntil()` の共通条件として描画回数が 0 より大きいことを要求する。空の結果を期待する場合も、初期状態だけでは成功させない。
- 操作後の描画を待つため、基準となる描画回数より後の結果を待てるようにする。回数、寸法、矩形の条件は同じロック下で評価する。
- ロック中の述語から `CanvasWidth()` など同じ mutex を取得するアクセサを呼ばない。述語へ必要な観測値を渡すか、ロックを取得済みの内部処理で判定する。
- 待機には既存の condition variable と有限のタイムアウトを使う。失敗時には基準回数、実測回数、キャンバス寸法、矩形を出力して原因を判断できるようにする。

### 極小状態で処理が継続することを確認する

- `TrackFixture` で、各ソースへの `InjectFrame()` が少なくとも 1 回完了したことを有限時間内に待てるようにする。`StartInjection()` を再度呼ぶ場合は、前回の注入完了を今回の完了として扱わない。
- 1x1 ウィンドウのケースでは、注入完了を確認した後に描画回数を取得し、その後に少なくとも 2 回描画されることを待つ。キャンバスが 1x1 で矩形が空であることを描画結果と同時に確認する。
- 続く `SetSize(2560, 1440)` 後も、新しい描画結果で 2 つの映像が期待する枠に復帰することを確認する。
- 1x2 ウィンドウのケースの固定 200 ms 待機も、注入完了とその後の描画継続を確認する待機へ置き換える。通常寸法に戻した後の既存の描画検証を維持する。
- 注入の 30 fps 制御に使う待機は維持する。テストの成功条件には実際の処理完了を使う。

変更対象は `test/base_renderer.cpp` の `TestRenderer`、`TrackFixture`、極小状態を扱うテストである。
`src/renderer/base_renderer.cpp` の `BaseRenderer::RenderThread()` は確認済みで、描画寸法を取得して `Render()` へ渡す実装になっている。
描画完了の観測と待機はテスト側で実装する。

## テスト戦略

実際の `BaseRenderer`、WebRTC トラック、映像フレーム、描画スレッドを使う。
モックやスタブは利用しない。

- テスト用レンダラーの自動起動を抑制できるようにし、描画未開始の状態で空の矩形を期待する待機がタイムアウトして false を返すことを確認する。実スレッドを `Start()` した後は、1x1 のキャンバスと空の矩形を観測できることを確認する。修正前の待機条件では前半が確実に失敗するため、偶然のスケジューリングに依存せず今回の不備を検出できる。
- 描画済みのレンダラーを `Stop()` し、その時点の描画回数を基準に新しい描画を待つとタイムアウトすることを確認する。過去の観測結果だけで待機が成功しないことを検証する。
- Windows で 1x1 の極小ウィンドウのケースを単独で 100 回実行し、失敗しないことを確認する。反復実行は安定性の補助確認とし、未開始状態の回帰テストでも原因を直接検出する。
- `base_renderer` の全ケースを Windows と macOS または Ubuntu で実行し、既存の拡大縮小、回転、複数映像の枠割りに回帰がないことを確認する。

## 完了条件

- 空の矩形を期待する待機が、初回描画前の初期状態だけで成功しない。
- 操作後の描画を待つ条件が、基準回数以前の観測結果だけで成功しない。
- 極小状態の 2 ケースが、各ソースへの注入完了と、その後の描画継続を有限時間内に確認する。
- 1x1 状態で 1x1 のキャンバスと空の矩形を確認でき、通常寸法に戻すと 2 つの映像が復帰する。
- 描画未開始と描画停止後の回帰テストが追加され、待機条件から描画回数の確認を外すと失敗する。
- Windows で該当ケースの 100 回実行が成功し、Windows と macOS または Ubuntu で `base_renderer` の全ケースが成功する。
- 待機条件のコメントに、初期状態と描画済みの空の結果を区別する理由が記載されている。
